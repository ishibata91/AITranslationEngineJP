# Investigation Module

## 目的

`investigation-module` は、人間が確認した不具合、レビュー非通過、検証失敗の観測記録から、実装モジュールへ渡せる「修正方針判断、UC 差分候補、E2E テスト観点差分、修正実行入力」を固定する設計モジュールの亜種である。
修正は fail-test ベースで進めるため、本モジュールの出口で先に不具合を検出できるテスト観点と修正方針を分けてから、実装モジュールへ渡す。

## 呼び出し関係

- 呼び出し元: 人間、または上位モジュール skill。
- 返却先: 呼び出し元。
- モジュールが呼ぶ下位 skill: `fix-decision`、`test-design`。
- モジュールが呼ぶ下位 agent: `fix_decider`、`test_designer`。

## 入口条件

- `preparation-module` の出口（作業 branch、`plan.md`）が固定されている、または同等の入力（作業 branch、依頼要約、`task-id`、active plan folder）が呼び出し元から渡されている。
- 人間観測記録（人間が見た画面、操作、ログ、失敗、期待との差分）が固定されている。
- 修正対象の Wails process または接続先が単一化されている。
- ブラウザ操作（`chrome-devtools` MCP ツール群、`mcp__plugin_chrome-devtools-mcp_chrome-devtools__*`）が利用できる。
- `想定 Y/N 評価` を本モジュールの最初に固定する。下位 agent 起動の前に行う。

## 出口条件

- `想定 Y/N 評価` が `plan.md` に固定されている。
- `修正方針判断` が `fix_decider` 担当の成果物として承認済み。
- `UC 差分候補` と `E2E テスト観点差分` が `test_designer` 担当の成果物として承認済み。
- `人間修正レビュー` 承認済み。
- `修正実行入力` が実装モジュールへ渡せる形で固定されている。
- 仕様変更または仕様追加が必要と判断された場合は停止して呼び出し元へ戻す（`design-module` への迂回が必要か、人間判断を仰ぐ）。

## 担当 artifact

| 成果物ID | 担当 | 依存対象 | 起動先 |
| --- | --- | --- | --- |
| `想定 Y/N 評価` | 呼び出し元 agent | `preparation-module` の出口 | なし |
| `人間観測記録` | 呼び出し元 agent | `想定 Y/N 評価` | なし |
| `修正方針判断` | `fix_decider` | `人間観測記録`, `事前準備` | `fix_decider` |
| `UC 差分候補` | `test_designer` | `人間観測記録`, `修正方針判断` | `test_designer` |
| `E2E テスト観点差分` | `test_designer` | `人間観測記録`, `修正方針判断` | `test_designer` |
| `人間修正レビュー` | 人間 | `修正方針判断`, `UC 差分候補`, `E2E テスト観点差分` | 人間 |
| `修正実行入力` | 呼び出し元 agent | `人間修正レビュー` | なし |

## 想定 Y/N 評価

- 本モジュールに入った直後、下位 agent を起動する前に、呼び出し元 agent が依頼要約と実コード（および関連する `docs/spec.md`、`docs/architecture.md`、active plan の既存成果物、観測記録）を読んで各想定の Y/N と根拠を `plan.md` に記録する。
- 評価する想定は次の 9 つ。1 想定 1 行で「Y/N、根拠 1 文、参照ファイルまたは仕様」を書く。
    - 仕様変更または仕様追加がある
    - 画面変更がある
    - 内部構造変更がある
    - 画面の表示変更がある（layout、文言、style、表示構造のいずれか。`storybook-module` の TRIGGER 軸）
    - frontend ロジック変更がある（state、API、Wails bridge、ルーティング、副作用、フォーム validation のいずれか。`implementation-module` の TRIGGER 軸）
    - backend 変更がある
    - frontend と backend を接続する
    - 実装済み責務を独立に証明したい
    - 実行時にしか確定しない値または原因分離が要る分岐がある
- 「仕様変更または仕様追加がある」が Y の場合は本モジュールを停止し、`design-module` への迂回が必要かを呼び出し元へ戻す。
- 評価結果は後続モジュール（`implementation-module`）が共通の入口として参照する。

`UC 差分候補` と `E2E テスト観点差分` は同じ `test_designer` 起動で同時に作成する。

## 各 artifact の詳細

### 人間観測記録

- 呼び出し元 agent が固定する。
- 不具合判断資料から、確認済みの不具合、期待との差分、観測された操作または条件を task 内成果物として固定する。
- 仮説や推測は含めない。観測事実のみを書く。

### 修正方針判断

- `fix_decider` を Task ツールで起動して作らせる。
- 下位 skill: `fix-decision`。
- 起動入力に含める内容: 人間観測記録、active plan folder、Wails 接続対象、画面設計書正本、ユースケース正本、観測ログ仕様。
- `fix_decider` は次を固定する。
    - 観測済み問題（人間観測記録から確認できる問題）。
    - 画面再現確認（`chrome-devtools` MCP ツールで画面設計のセレクタに従って再現した結果）。
    - 原因仮説（複数仮説と検証順序）。
    - 観測ログ検証（一時ログ追加、観測結果、削除確認）。
    - 確定原因（観測で確定したもののみ）。
    - 採用する修正方針（仕様が不足していない時のみ）。
    - 禁止する修正（新しい状態値の追加、症状だけを隠す分岐などを具体的に）。
- 呼び出し元 agent と本モジュール skill は `修正方針判断` 本文を代筆しない。

### UC 差分候補

- `test_designer` を Task ツールで起動して作らせる。
- 下位 skill: `test-design`。
- 既存ユースケース記述に対する差分候補を次の分類で固定する。

| 分類 | 意味 |
| --- | --- |
| `差分なし` | 既存ユースケースで問題と期待状態を説明できる状態。 |
| `記述不足` | 既存期待を説明するフロー、例外、境界の記述が不足している状態。 |
| `新規判断必要` | 既存期待では説明できない仕様変更または機能追加の判断が必要な状態。 |

- `新規判断必要` が含まれる場合は本モジュールを停止し、`design-module` 経由の仕様変更が必要かを人間へ戻す。

### E2E テスト観点差分

- `test_designer` を Task ツールで起動して作らせる（`UC 差分候補` と同時起動）。
- 下位 skill: `test-design`。
- E2E テスト観点正本に対する差分を次の分類で固定する。

| 分類 | 意味 |
| --- | --- |
| `差分なし` | E2E テスト観点正本に修正対象を証明する観点が既にある状態。 |
| `追加候補あり` | E2E テスト観点正本に対し、修正対象を証明する観点が不足している状態。 |
| `判断不足` | 人間レビューで期待値または対象画面を確認しないと観点を固定できない状態。 |

- `判断不足` が含まれる場合は `人間修正レビュー` で固定する。

### 人間修正レビュー

- `修正方針判断`、`UC 差分候補`、`E2E テスト観点差分` が揃った時点で人間へ返す。
- 差し戻しまたは追加質問の場合は、対象成果物を作った同じ agent を再起動して引き継ぎ入力に差し戻し内容を明示する。新規 agent を起こさない。
- 承認時に「採用する修正方針」「承認済み UC 差分」「承認済み E2E テスト観点差分」が固定される。

### 修正実行入力

- 呼び出し元 agent が固定する。
- 次を実装モジュールへ渡す入力として `plan.md` に記録する。
    - 承認済み修正方針（恒久修正として採用する方針）。
    - 禁止する修正（実装 agent に許可しない対症療法）。
    - 影響ファイル候補（`fix_decider` が観測事実に基づき返した候補。実装 agent の変更ファイルは確定しない）。
    - 承認済み UC 差分（記述不足分の埋め先）。
    - 承認済み E2E テスト観点差分（追加候補と判断不足の確定結果）。
    - 画面再現確認の再現手順と修正後に満たすべき期待状態（実装モジュールが利用する）。

## 不変条件

### 修正方針判断の必須観点

| 観点 | 拘束する判断 |
| --- | --- |
| `観測済み問題` | 人間観測記録から確認できる問題だけを固定する。 |
| `画面再現確認` | 画面設計のセレクタに従い、人間観測記録のユーザー操作を `chrome-devtools` MCP ツールで再現する。 |
| `原因仮説` | 観測事実から複数の原因候補を立て、検証する順序と根拠を固定する。 |
| `観測ログ検証` | 仮説を否定または支持するために追加した一時ログ、観測結果、削除確認を固定する。 |
| `確定原因` | 観測で確定した原因だけを固定する。 |
| `採用する修正方針` | 仕様が不足していない場合だけ恒久修正を固定する。 |
| `禁止する修正` | 新しい状態値の追加、症状だけを隠す分岐などを具体的に固定する。 |

### 責務境界

- `fix_decider`、`test_designer` の担当 artifact 本文を呼び出し元 agent と本モジュール skill が代筆しない。
- 起動先 agent には会話文脈を引き継がず、必要情報を引き継ぎ入力へ明示する。起動先 agent に下位 agent を起動させない。
- 影響ファイルは候補として扱う。実装 agent の変更ファイルを本モジュールで確定しない。

### 安全境界

- 一時観測ログ以外のプロダクトコード変更は本モジュールでは行わない。
- プロダクトテスト変更、docs 正本本文変更は本モジュールでは行わない。
- 追加した一時観測ログは `修正方針判断` を返す前に削除する。

### 仕様不足の停止

- `UC 差分候補` に `新規判断必要` が含まれる場合、または `fix_decider` が修正方針を仕様変更・機能追加・受け入れ条件の新規判断と判断した場合は、本モジュールを停止する。停止時は呼び出し元へ「`design-module` 経由の仕様変更が必要」と戻す。

## 返す成果物

- 観測済み問題: 根拠から確認できる問題。
- 画面再現確認: 再現手順、操作結果、画面状態、証跡参照。
- 確定原因: 観測で確定した原因。
- 採用する修正方針: 恒久修正として採用する方針。
- 禁止する修正: 実装 agent に許可しない対症療法。
- 承認済み UC 差分: 記述不足分の埋め先。
- 承認済み E2E テスト観点差分: 追加候補と判断不足の確定結果。
- 影響ファイル候補: 観測事実に基づく候補。
- 修正実行入力: 実装モジュールへ渡す入力一式。
- 停止判定: 停止理由、不足項目、戻し先。

## 作業を止める条件

- `想定 Y/N 評価` を下位 agent 起動の前に固定できない。
- `想定 Y/N 評価` で「仕様変更または仕様追加がある」が Y と判定された（呼び出し元へ戻し、`design-module` への迂回判断を仰ぐ）。
- 人間観測記録が不足する。
- Wails 接続対象が単一化されていない。
- 画面設計の selector に従ったユーザー操作を `chrome-devtools` MCP ツールで再現確認できない。
- 観測ログを追加または確認できず、仮説を検証できない。
- 追加した一時観測ログを削除できない。
- 原因が仮説に留まり、採用する修正方針を固定できない。
- `UC 差分候補` に `新規判断必要` が含まれる、または `fix_decider` が仕様変更・機能追加・受け入れ条件の新規判断が必要と判断した。
- `人間修正レビュー` 承認が得られない、または差し戻しを解消できない。
- 停止時は不足項目、衝突箇所、固定できない判断、戻し先を返す。
