# Presentation

## 目的

`presentation` は、人間が読んで判断するための、わかりやすい説明 md を Claude 本体が作る時の作業プロトコルである。
説明文と図を 1 つの md に統合し、読み手が「何が」「なぜ」「どうなる」を再解釈なしに読める状態を作る。
成果物は task 内の判断材料として扱う。

`presentation` は、人間が読んで判断する説明 md、現況/あるべき形 変更図、明示された補助図を扱う。設計レビュー材料、修正方針の説明、調査結果の共有などが該当する。
特定の module に依存しない。呼び出し元が固有のセクションや図を指定する場合は、呼び出し元の指定に従う。
目的に合わない旧規約は作り直してよい。

## 対応役割

- Claude 本体が task 文脈を持ったまま読んで適用する。
- 呼び出し元は、人間、または説明 md・図が判断補助に要る module とする。特定の module には依存しない。
- 担当成果物は `説明 md`、`現況/あるべき形 変更図`、明示された補助図とする。

## 呼び出し元から渡される情報

- 必須呼び出し元: 説明 md を依頼した module または人間。
- 必須提示目的: 説明 md と図で人間または呼び出し元が固定する判断。
- 必須根拠参照: 説明と図の根拠にする task 内成果物または docs 正本。
- 必須作業計画フォルダ: 成果物を置く `docs/exec-plans/active/<task-id>/`。
- 必須成果物種別: `説明 md`、`現況/あるべき形 変更図`、明示された補助図のいずれか。
- 非必須予定変更箇所: 追加予定箇所、削除予定箇所、変更しない接続先。
- 非必須確認してほしい点: 人間レビューで確認を促す制約、注意、残る判断。
- 非必須寿命指定: 呼び出し元が決める成果物の寿命（一時か保持か）。
- 非必須禁止範囲: 説明 md または図に含めてはいけない範囲。

## 作業前に読む正本

- Mermaid を含む Markdown を成果物の正本とする。
- 成果物の置き場所は作業計画フォルダ（`docs/exec-plans/active/<task-id>/`）とする。
- 雛形は持たない。図と構成は題材ごとに最適なものを選ぶ。
- 外部成果物が不足または衝突する場合は停止し、衝突箇所を返す。

## 担当役割が判断してよい範囲

わかりやすさの判断は、確立した資料設計の原則に沿わせる。原則名は意味を添えて残す。

### 構成の順序

- 結論を先に書く。全体を要約する主張を最初に置き、結論の後に根拠と詳細を続ける（ピラミッド原則の結論ファースト）。
- 1 つの md で読み手に残す主張を 1 つに絞る。「何が言いたいか」と「なぜ重要か」を冒頭で答える。
- 内容をグループに分け、各グループ内は同じ種類の項目だけにし、論理順に並べる（ピラミッド原則のグループ化。重複と漏れのない分け方にする）。

### 文

- 1 文 1 論点にする。1 文を長くしすぎない。
- 専門語と固定名は、最初に意味を 1 文で添える。
- 抽象語より具体語を使う。

### 視覚（レイアウトと強調）

- 関連する要素を近づけ、関連しない要素は余白で離す（近接）。
- 見出し、記号、用語の体裁を統一する（反復）。
- 重要要素はサイズや位置で強弱をつけて強調する（対比）。
- 判断に不要な要素は落とし、情報を詰め込みすぎない（関連情報の比率を上げる）。
- 読み手の視線の流れ（横書きは上から下、左から右）に沿って並べる。

### 構成は題材に最適化する

- 題材ごとに、最適な図と説明したい論点を選ぶ。
- 次は人間が判断する材料でよく要る論点の候補とする。当たるものだけ選び、順序は題材の主張に合わせて決める。
    - 主張: 説明 md で何を判断してほしいか。
    - 背景と課題: なぜ判断が要るか。
    - 根拠と方針: 何を選び、なぜ選んだか。検討した代替案があれば却下理由も添える。
    - 影響と注意: 変わる範囲と、見落としてはいけない点。
    - 確認してほしい点: 残る判断。
- 候補にない論点でも、題材の判断に要るなら加える。要らない論点は落とす。
- 機械向け handoff 成果物があれば参照で示す。未確定なら方針の要点だけ示す。
- 呼び出し元が固有の論点（製品固有の影響範囲、テスト方針など）を指定する場合は、呼び出し元の指定に従う。

### 図

- 図種別は固定しない。主張を最も伝える図（コンポーネント図、シーケンス図、状態図、フロー図、ER 図など）を題材ごとに選ぶ。構造の差分は箱と接続、時系列の差分は呼び出し順、状態の差分は遷移で示す。
- 図は Mermaid で作り、説明 md に埋め込む。
- 変更差分は 現況とあるべき形の 2 図で示す。読み手は 2 図を見比べて差分を読む。
- 現況とあるべき形 は同じ図種別、同じ並び、同じ命名で描き、変わった箇所だけが差として浮かぶようにする。
- 2 図で読み取りにくい差分（消えた要素、増えた要素など）は、本文で「現況 から消える要素」「あるべき形 で増える要素」として言葉でも補う。
- 1 枚の図は、16:9 のプレビュー（スライド枠や画面幅）に収めても文字が読める大きさに保つ。
- 1 枚に詰める要素（箱、参加者、ノード）は 7 個前後を目安にする。超える、または図が縦か横へ伸びて 16:9 の枠で縮むなら、主張の単位で複数の図に分割する。
- 図の方向は、16:9 の枠に収まりやすい形を選ぶ。縦に長くなりすぎる図は、グループで分けるか方向を変える。
- 現況/あるべき形 変更図は、予定変更箇所と接続先の最小範囲を 2 図で示す。予定変更箇所以外を網羅図として含めない。
- シーケンス図は、参加者、呼び出し順序、分岐が図内で読める場合、Mermaid だけでよい。
- 箱で示す図（コンポーネント図、構成図、状態図）は、概要と各要素の説明を Markdown に置く。
- 目的に合わない古い図規約は、互換目的で残さない。

## skill が扱わない対象

- プロダクトコードの変更は扱わない。
- プロダクトテストの変更は扱わない。
- docs 正本図、docs 正本本文の更新は扱わない。
- 画面表示の設計（Storybook の story とコンポーネント）は扱わない。
- 機械向け handoff 成果物の本文確定は扱わない（呼び出し元が別に固定する）。
- 成果物の寿命決定は扱わない（呼び出し元の規約に従う）。

## 返す成果物

- 判断結果: 説明 md 作成の完了、未完了、停止の判定を返す。
- 成果物種別: 扱った `説明 md`、`現況/あるべき形 変更図`、補助図の種別を返す。
- 成果物path: 作成または更新した Markdown の path を返す。
- 根拠参照: 説明と図の根拠にした task 内成果物または docs 正本を返す。
- 含めない範囲: 出力に含めなかった機械向け handoff 本文、画面表示設計、正本変更を返す。
- 検証結果: Markdown 確認と Mermaid 記述確認の結果を返す。
- 不足情報: 説明 md を完了できない不足項目を返す。

## 作業を完了できる条件

- 説明 md の path が返っている。
- 説明 md が、読み手の「何が」「なぜ」「どうなる」を再解釈なしに読める構成になっている。
- 根拠参照が返っている。
- 図を含む場合、Mermaid コードブロックが壊れずに揃っている。
- 図を含む場合、1 枚が 16:9 のプレビューで文字が読める大きさに収まっている。収まらないものは分割している。
- `現況/あるべき形 変更図` の場合は、現況とあるべき形 の 2 図が揃い、同じ図種別・並び・命名で描かれている。
- `現況/あるべき形 変更図` の場合は、図の概要と各要素の説明が揃い、2 図で読み取りにくい差分は本文で補われている。
- 機械向け handoff 本文が参照で示されている。

## 作業を止める条件

- 必須呼び出し元、必須提示目的、必須根拠参照、必須作業計画フォルダのいずれかが不足する。
- 必須成果物種別が不足する。
- `現況/あるべき形 変更図` で 現況とあるべき形 の 2 図が揃わない、または予定変更箇所以外を網羅図として含む。
- Markdown 図成果物の Mermaid コードブロックが壊れている。
- 図化と説明の範囲を越え、仕様変更や機能追加が要ると判明した（呼び出し元、または仕様変更を扱う module へ戻す）。
- 停止時は不足項目、衝突箇所、戻し先を返す。
