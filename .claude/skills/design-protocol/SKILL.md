# Design Protocol

## 目的

`design-protocol` は、`design.md` と `spec.md` の書き方と、両者に対する `design-review` の検証内容を固定する作業プロトコルである。
新規実装フロー（`feature-workflow`）と修正フロー（`fix-workflow`）が同じ規約を読む。各入口 skill は、いつ書くか（依存順、承認順）を持つ。

`design.md` は人間が読んで判断する説明を持つ。`spec.md` は下流の段が実装根拠にする対象集合と期待値を持つ。両者が食い違う場合は `spec.md` を優先する。

## 対応役割

- Claude 本体が task 文脈を持ったまま読んで適用する。
- `design-review` は `design_reviewer` agent（`fresh`、読み取り専用）が担う。
- 呼び出し元は `feature-workflow`、`fix-workflow`、または同等の入力を渡す上位 skill とする。

## 呼び出し元から渡される情報

- task-id: 作業計画フォルダを特定する識別子。
- 作業計画フォルダ: `design.md` と `spec.md` を置く `docs/exec-plans/active/<task-id>/`。
- フロー種別: 新規実装フローと修正フローのどちらか。
- 根拠: 新規実装フローは人間の依頼要約と `plan.md`、修正フローは `investigation.md` の確定原因。

## 作業前に読む正本

- `design.md` の雛形: `docs/exec-plans/templates/task-folder/design.md`。
- `spec.md` の雛形: `docs/exec-plans/templates/task-folder/spec.md`。
- 図作法: `presentation` skill。
- 外部成果物が不足または衝突する場合は停止し、衝突箇所を返す。

## design.md

`design.md` は次の 2 つを持つ。

- 実装方針: どう実装し、どう変えるかを文章で書く。現状（AS-IS）と変更後（TO-BE）を対にして、何がどう変わるかを示す。対応は雛形の表で書き、AS-IS には根拠となるソースの場所（file・関数・table 名）を、TO-BE には変更予定の場所と「どこをどう変えれば TO-BE が成立するか」の実現主張を添える。場所を挙げられない TO-BE は書かない。どこまで動かすか（task 後に観測できる振る舞い）と観測点（単体テスト・実画面・実データのいずれか）を含める。最小実装・仮実装・空テーブルだけで goal を満たしたことにしない。
- 検討が必要なこと: 人間の回答なしに先へ進めない未解決の論点。論点がなければ「なし」と書く。

フロー種別で次を足す。

| フロー種別 | 実装方針に足すこと |
| --- | --- |
| 新規実装フロー | 新規実装で現状が無い行は AS-IS を「なし」と書く |
| 修正フロー | `investigation.md` の確定原因に対応する直し方を書く。症状だけを隠す対症療法（新しい状態値の追加、症状を隠す分岐）を避ける |

流れ・関係・責務が変わる箇所は、AS-IS と TO-BE の 2 図を文章に添える。図作法は `presentation` skill に従う。図を添える場合も、説明は文章で成立させる。

## spec.md

`spec.md` は次の 2 つを持つ。設計理由、変更手順、図は `design.md` が持つ。

- 対象集合: この task の処理対象に含むものと含まないものを、それぞれ肯定形で列挙する。読み手が範囲を 1 通りに取れる粒度で書く。
- 期待値表: 1 行 1 期待値で、AS-IS の期待値（現状で成立している振る舞い。現状が無い行は「なし」）と TO-BE の期待値（変更後に成立させる振る舞い）を横に並べる。

記述を次に拘束する。

- 主語と目的語を書く。何が、どの条件で、どうなるかを 1 文で示す。
- TO-BE の期待値の語尾は「〜こと」で終える。この文をそのまま実テストの test case 名として使う。
- 1 通りにしか読めない語を選び、同じ対象は同じ語で呼ぶ。
- 対象に含む側の境界と含まない側の境界を、それぞれ独立した 1 行として立てる。

フロー種別で次を足す。

| フロー種別 | 期待値表に足すこと |
| --- | --- |
| 新規実装フロー | AS-IS の期待値は現状で成立している振る舞いとする |
| 修正フロー | AS-IS の期待値は不具合時に観測された振る舞いとする。TO-BE の期待値は、実装への引き継ぎで渡す fail-test の観点と同じ文にする |

「対応する実テスト」列は本 skill では空にする。`implementation-module` が最終検証で埋める。

## design-review

`design-review` は、人間レビューの前に、実現可能でない案と誤読の余地がある記述を否決して人間との往復を減らす AI 検証である。両フローで通す。

- 入力: `design.md` のパス、`spec.md` のパス、`task-id`、対象 repo のルート、フロー種別。
- 検証内容:
    - AS-IS 検証: `design.md` の AS-IS 記述を根拠ソースの場所と照合し、現状認識が実ソースで成立しているかを確かめる。
    - TO-BE 検証: 変更予定箇所の実現主張を実ソースへ踏み込んで確かめ、成立しない主張を否決する。
    - 漏れ検出: 変更予定箇所の列挙から漏れた影響先（呼び出し元、依存先、同じ前提を持つ別箇所）を確かめる。
    - 記述検証: `spec.md` の対象集合が肯定形で列挙されているか、主語と目的語が書かれているか、TO-BE の期待値の語尾が「〜こと」で終わっているか、各行が 1 通りにしか読めないかを判定する。読み手が範囲を広くも狭くも取れる行は、該当行を挙げて否決する。
    - 整合検証: `design.md` の TO-BE と `spec.md` の期待値が同じ振る舞いを指しているかを確かめる。`design.md` にあって期待値表に無い振る舞いは漏れ候補として返す。
- 修正フローで足す検証: `design.md` の修正方針が `investigation.md` の確定原因に対応しているかを確かめる。確定原因から離れた直し方は否決する。
- 判断範囲: 成立可否の判定、記述違反の指摘、漏れの指摘だけを行う。設計の好み、代替案の選定、実装、`design.md` と `spec.md` の書き換えは呼び出し元が扱う。
- 出力: 判定（通過または否決）、否決理由（照合したソースの場所または該当行つき）、漏れ候補の一覧。戻し先は呼び出し元。
- 否決時: Claude 本体が同じ文脈で `design.md` または `spec.md` を書き直し、`design-review` を再実行する。否決理由を解消できない場合は人間へ論点として上げる。

## skill が扱わない対象

- いつ書くか（依存順、承認順、下流への引き継ぎ）は各入口 skill が扱う。
- 実装範囲の scope 列挙とテスト設計は `implementation-module` が扱う。
- 再現確認と原因究明は `fix-decision` と `investigation.md` が扱う。
- 人間レビューの依頼と承認判定は各入口 skill が扱う。
- docs 正本反映は `finalization-module` が扱う。

## 返す成果物

- design.md パス: 作成または更新した `design.md` の場所。
- spec.md パス: 作成または更新した `spec.md` の場所。
- 確定仕様の要約: `spec.md` の対象集合と TO-BE の期待値。
- design-review 判定: 通過または否決、否決理由、漏れ候補。
- 未解決の論点: `検討が必要なこと` に残る、人間回答が要る論点。

## 作業を完了できる条件

- `design.md` に実装方針と検討が必要なことが書かれている。
- `spec.md` に対象集合と期待値表が書かれ、記述の拘束を満たしている。
- `design-review` の判定が、全 AS-IS 根拠、全 TO-BE 実現主張、対象集合、全期待値行に付いている。
- `design-review` が通過している。

## 作業を止める条件

- 作業計画フォルダ、フロー種別、根拠のいずれかが不足する。
- 対象集合または期待値を肯定形で固定できない（何を含めるかが人間回答なしに確定しない）。
- `design.md` に根拠ソースの場所または変更予定箇所を書けない。
- `design-review` の否決理由を書き直しで解消できない。
- 停止時は不足項目、衝突箇所、固定できない判断、戻し先を返す。
