# Refactor Lane

## 目的

`refactor-lane` は、既存仕様と既存実装のずれを先に整理し、人間判断で正とする側を固定した後、責務過多、責務分離不足、コーディング規約逸脱、構造設計正本との不整合、既存テストの品質と仕様整合性を調査し、承認済み `implementation-scope` に基づいて修正する作業プロトコルである。
この skill は、新しい機能要求を作らず、既存仕様、既存実装、既存テスト、人間判断、構造品質調査、テスト品質調査の範囲内でリファクタ対象を固定するために使う。

## 対応ロール

- `refactor_lane` が使う。
- 呼び出し元は人間とする。
- 返却先は人間とする。
- 担当成果物は `task 枠`、`branch 準備`、`仕様乖離整理`、`仕様実装優先判断`、`構造品質調査`、`テスト品質調査`、`リファクタ範囲確認`、`実装範囲`、`実装引き継ぎ入力`、`backend リファクタ`、`frontend リファクタ`、`統合境界リファクタ`、`シナリオテスト`、`単体テスト`、`最終検証`、`実装後ブラウザ確認`、`レビュー通過根拠`、`docs正本化判断`、`詳細仕様正本反映`、`作業 commit`、`マージ準備入力` とする。
- 起動担当 agent は `investigator`、`designer`、`backend_implementer`、`frontend_implementer`、`integration_implementer`、`implementation_scenario_tester`、`implementation_unit_tester`、`browser_confirmation`、観点別レビュー agent、`docs_updater` とする。

## 入力規約

- 呼び出し元: この skill を呼び出した人間。
- 依頼要約: リファクタとして扱う依頼内容。
- 作業計画フォルダ: task 内成果物を置く `docs/exec-plans/active/<task-id>/`。
- 作業場所: Codex app が用意した実行場所。
- 作業ブランチ: 既定名 `codex/<task-id>` の local branch。
- 統合先ブランチ: 既定名 `master` の local branch。
- 対象仕様参照: 仕様乖離整理で照合する docs 正本、詳細仕様正本、画面設計正本。
- 対象実装範囲: 仕様乖離整理と構造品質調査で読むプロダクトコード範囲。
- 対象テスト範囲: テスト品質調査で読むプロダクトテスト範囲。
- 変更禁止範囲: 人間が変更してはいけないと指定した範囲。
- 既存成果物: 作業計画フォルダに既にある task 内成果物。
- 人間介入状態: 仕様実装優先判断、リファクタ範囲確認、承認、差し戻し、追加質問の記録。
- ハーネス要件: リファクタ終了前に通す検証 suite と command。

### 仕様乖離分類

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| `仕様が正` | docs 正本が正しく、実装が古いまたは好ましくない状態 | 承認済み code 修正候補にする |
| `実装が正` | 実装が正しく、docs 正本が古いまたは好ましくない状態 | docs 正本化候補にし、code 修正候補にしない |
| `判断保留` | 人間判断が不足し、仕様と実装のどちらを正にするか決められない状態 | 停止する |
| `対象外` | 今回のリファクタ範囲に含めない仕様乖離 | 実装範囲に含めない |

## 判断規約

- 次の実行判断は成果物DAGの未完了成果物、満たされた `依存対象`、既存成果物、対象 skill の完了規約で決める。
- `task 枠` はリファクタ目的、対象仕様参照、対象実装範囲、対象テスト範囲、変更禁止範囲、検証要件を含める。
- `branch 準備` は active plan ごとの作業ブランチと統合先ブランチを作成または確認する。
- `仕様乖離整理` は `investigator` を起動して作る。
- `仕様乖離整理` は docs 正本と対象実装範囲を照合し、仕様と実装の差だけを記録する。
- `仕様乖離整理` は仕様と実装のどちらが正しいかを AI だけで決めない。
- `仕様実装優先判断` は人間が仕様乖離ごとに `仕様が正`、`実装が正`、`判断保留`、`対象外` のいずれかを選んだ状態を指す。
- `仕様が正` の項目は code 修正候補にできる。
- `実装が正` の項目は docs 正本化候補にし、code 修正候補にしない。
- `判断保留` がある場合は、該当項目を実装範囲へ入れない。
- 新しい親要件、受け入れ条件、公開契約、永続仕様が必要な場合は、新規実装レーンまたは docs 正本化判断へ戻す。
- 人間が確認した不具合、レビュー非通過、検証失敗の恒久修正が主目的になる場合は、修正レーンへ戻す。
- `構造品質調査` は `investigator` を起動して作る。
- `構造品質調査` は仕様実装優先判断で固定された正しい振る舞いを前提にする。
- `構造品質調査` は責務過多、責務分離不足、コーディング規約逸脱、構造設計不整合を根拠別に分ける。
- `構造品質調査` は変更不要範囲を明示し、変更不要範囲を実装範囲へ含めない。
- `テスト品質調査` は `investigator` を起動して作る。
- `テスト品質調査` は `investigate` の判断規約と完了規約に従う。
- `リファクタ範囲確認` は人間が構造品質調査とテスト品質調査のうち実装範囲へ入れる項目を承認した状態を指す。
- `実装範囲` は `designer` を起動し、`implementation-scope` に従って作る。
- `implementation-scope` には、仕様実装優先判断、リファクタ範囲確認、構造品質調査、テスト品質調査、対象実装範囲、対象テスト範囲、変更禁止範囲、検証要件を渡す。
- `implementation-scope` は backend、frontend、統合境界、シナリオテスト、単体テストを必要に応じて別引き継ぎに分ける。
- `実装引き継ぎ入力` は承認済み `implementation-scope` から作る。
- 起動先 agent には文脈を引き継がず、必要情報を引き継ぎ入力に明示する。
- `backend リファクタ` は backend 責務内の承認済み実装範囲だけを扱う。
- `frontend リファクタ` は frontend 責務内の承認済み実装範囲だけを扱う。
- `統合境界リファクタ` は API、Wails、DTO、gateway、adapter 契約の承認済み統合境界だけを扱う。
- リファクタで振る舞いを変えない項目は、既存振る舞いを守るテストまたは検証を完了条件へ含める。
- 仕様乖離解消で振る舞いが変わる項目は、`仕様が正` の人間判断と対応する仕様根拠を完了条件へ含める。
- `シナリオテスト` は公開接点または UI 人間操作起点の振る舞いを保護する場合だけ起動する。
- `単体テスト` は分岐、変換、境界、責務分離後の局所振る舞いを保護する場合だけ起動する。
- `最終検証` は承認済み実装範囲と touched-layer の検証結果を記録する。
- `実装後ブラウザ確認` は UI 表示、UI 導線、frontend と backend の接続が触れた場合だけ起動する。
- `レビュー通過根拠` は観点別レビュー agent を起動し、挙動正しさ、契約・互換性、権限・信頼境界、状態・データ不変条件、責務境界を確認する。
- `docs正本化判断` は `実装が正` の仕様乖離がある場合だけ、docs 正本化起動入力を作る。
- `詳細仕様正本反映` は人間承認済み docs-only 成果物だけを `docs_updater` へ渡す。
- `マージ準備入力` は active plan folder、作業ブランチ、統合先ブランチ、commit hash、検証結果、レビュー結果、docs 正本化結果、残留リスクを含める。
- 作業計画フォルダの completed 移動と local merge は `merge_lane` に渡す。
- プロダクトコードとプロダクトテストは直接変更しない。

## 非対象規約

- 新規実装と機能拡張の初期設計は扱わない。
- 人間が確認した不具合、レビュー非通過、検証失敗の恒久修正を主目的にしない。
- 探索テストの計画と観測は扱わない。
- Storybook 上の人間指摘を起点にした UX 保守は扱わない。
- 仕様実装優先判断なしで仕様乖離を解消しない。
- リファクタ範囲確認なしで構造品質調査の項目を実装範囲へ入れない。
- リファクタ範囲確認なしでテスト品質調査の項目を実装範囲へ入れない。
- 承認済み `implementation-scope` 外のプロダクトコードとプロダクトテストを扱わない。
- docs 正本本文を直接更新しない。
- 起動先 agent の下位 agent 起動は扱わない。
- local merge、completed 移動、remote repository の変更は扱わない。

## 停止規約

- 対象仕様参照、対象実装範囲、対象テスト範囲のうち必要な参照が不足する場合は停止する。
- 作業計画フォルダ、作業ブランチ、統合先ブランチを判断できない場合は停止する。
- 仕様乖離で仕様と実装のどちらを正とするか人間判断が不足する場合は停止する。
- 人間判断なしで docs 正本または実装を古いと断定しそうな場合は停止する。
- `リファクタ範囲確認` が不足する場合は停止する。
- 新しい親要件、受け入れ条件、公開契約、永続仕様が必要な場合は停止する。
- 人間が確認した不具合、レビュー非通過、検証失敗の恒久修正が主目的になる場合は停止する。
- 承認済み `implementation-scope` が不足する場合は停止する。
- 承認済み `implementation-scope` 外へプロダクトコードまたはプロダクトテストの変更を広げる必要がある場合は停止する。
- 変更不要範囲を変更する必要がある場合は停止する。
- 変更不要テスト範囲を変更する必要がある場合は停止する。
- docs 正本化に必要な人間承認が不足する場合は停止する。
- ハーネスが通らない場合は停止する。
- 観点別レビューで修正必須指摘が未解決の場合は停止する。
- local commit を作成できない場合は終了不可とする。
- `マージ準備入力` が不足する場合は終了不可とする。
- local merge または completed 移動を実行しそうな場合は停止する。
- `push`、tag push、remote branch delete など remote repository を変更しそうな場合は停止する。
- 停止時は不足項目、衝突箇所、固定できない判断、戻し先を返す。
