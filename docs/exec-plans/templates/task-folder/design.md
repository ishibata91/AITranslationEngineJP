# Design: <task-id>

`design.md` は実装方針と検討が必要なことを持つ。
実装範囲の scope 列挙とテスト設計は持たない（実装モジュールが扱う）。

新規実装フロー（`feature-workflow`）は下の 2 節をそのまま使う。
修正フロー（`fix-workflow`）は「実装方針」を `fix-decision` の修正方針判断（観測済み問題・画面再現確認・原因仮説・観測ログ検証・確定原因・採用する修正方針・禁止する修正）と修正実行入力（承認済み修正方針・禁止する修正・影響ファイル候補・再現手順と期待状態・追加する fail-test の観点）へ置き換える。

## 実装方針

どう実装し、どう変えるかを文章で書く。
現状（AS-IS）と変更後（TO-BE）を対にして、何がどう変わるかを文章で示す。どこまで動かすか（task 後に観測できる振る舞い）と、その観測点（単体テスト・実画面・実データのいずれか）も含める。最小実装・仮実装・空テーブルだけで goal を満たしたことにしない。

流れ・関係・責務が変わる箇所は、図を文章に添えるとわかりやすい。図種別（ER 図、コンポーネント図など）は題材に合わせ、AS-IS（現状）と TO-BE（変更後）の 2 図で示す。色で塗り分ける差分図は使わない。図作法は `presentation` skill に従う。図を添える場合も文章を省かず、図だけで説明しない。
