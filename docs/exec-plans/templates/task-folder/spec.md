# Spec: <task-id>

`spec.md` はこの task の確定仕様として、要求ごとの仕様を持つ。要求は `plan.md`、設計理由・変更手順・図は `design.md` が持つ。
`design.md` と `spec.md` が食い違う場合は `spec.md` を優先する。
設計フロー（`design-workflow`）と修正フロー（`fix-workflow`）が同じこのテンプレートを使う。

`plan.md` の要求ごとに節を分け、節と節の間に区切り線を置く。どの要求の節にも置けない仕様は書かない。置き場所が無い仕様は、`plan.md` の要求欄へ足すことを人間へ諮るか、捨てる。

書き方を次に拘束する。

- 仕様の主語と目的語は、要求の文に現れる語か、`docs/vocabulary.md` にある語で書く。
- 新しい名詞が要る場合は、`docs/vocabulary.md` へ足すことを人間へ諮る。足さない場合は名詞を作らず、動作を説明する文で書く。
- 仕様の語尾は「〜こと」で終える。この文をそのまま実テストの test case 名として使う。
- 確かめ方が空欄になる仕様は、要求から見えない仕様なので捨てる。
- 各要求の節に、正常系、対象に入る側の境界、対象に入らない側の境界の 3 つを揃える。書けないものがある場合は、理由を `design.md` の `検討が必要なこと` へ書く。

    - 前提条件: <対象の端にある状況を書く>
    - 確かめ方: <同上>

- R-1-3（対象に入らない側の境界）: <要求が扱う対象の外にあり、要求どおりの動きをしない振る舞いを「〜こと」で書く>
    - 前提条件: <対象の外にある状況を書く>
    - 確かめ方: <同上>
    - 対応する実テスト:

**満たさない部分**: <要求のうち今回満たさない部分を 1 文で書く。無ければこの行を置かない。>

---

前提条件に「なし」と書いた仕様が、状況によらず成立させる振る舞いになる。
「対応する実テスト」は設計段階では空にする。`implementation-workflow` の `implementer` が最終検証で埋め、対応する実テストを置けなかった仕様は停止理由または残課題として人間へ上げる。
