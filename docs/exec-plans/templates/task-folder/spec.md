# Spec: <task-id>

`spec.md` はこの task の確定仕様として、対象集合と期待値表を持つ。設計理由・変更手順・図は `design.md` が持つ。
`design.md` は人間が読んで判断する説明を持つ。`design.md` と `spec.md` が食い違う場合は `spec.md` を優先する。
新規実装フロー（`feature-workflow`）と修正フロー（`fix-workflow`）が同じこのテンプレートを使う。

書き方を次に拘束する。

- 対象集合は、含むものと含まないものをそれぞれ肯定形で列挙する
- 主語と目的語を書く。何が、どの条件で、どうなるかを 1 文で示す。
- TO-BE の期待値の語尾は「〜こと」で終える。
- 1 通りにしか読めない語を選び、同じ対象は同じ語で呼ぶ。
- 対象に含む側の境界と、含まない側の境界を、それぞれ独立した 1 行として立てる。

## 対象集合

- 含む: <この task の処理対象に入るものを肯定形で列挙する。>
- 含まない: <処理対象に入らないものを肯定形で列挙する。>

## 期待値

1 行 1 期待値で書く。TO-BE の期待値の文は、そのまま実テストの test case 名として使う。

| # | AS-IS の期待値 | TO-BE の期待値 | 対応する実テスト |
| --- | --- | --- | --- |
| 1 | <現状で成立している振る舞い。現状が無い行は「なし」と書く> | <変更後に成立させる振る舞いを「〜こと」で書く> | <`implementation-module` が最終検証でテストの file と test case 名を書く> |

「対応する実テスト」列は設計段階では空にする。`implementation-module` が最終検証で埋め、対応する実テストを置けなかった行は停止理由または残課題として人間へ上げる。
