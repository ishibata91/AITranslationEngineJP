# Design: <task-id>

`design.md` は修正方針判断、修正実行入力、検討が必要なことを持つ。
実装範囲の scope 列挙とテスト設計は持たない（実装モジュールが扱う）。
修正フロー（`fix-workflow`）はこのテンプレートを `design.md` として使う。修正方針判断は `fix-decision` skill を読んで適用する。

## 修正方針判断

- 観測済み問題: 人間観測記録から確認できる問題だけを書く。
- 画面再現確認: 実装済み画面の `data-testid` またはセレクタに従い、人間観測記録のユーザー操作を `chrome-devtools` MCP ツールで再現した結果。
- 原因仮説: 観測事実から立てた複数の原因候補と、検証する順序と根拠。
- 観測ログ検証: 仮説を否定または支持するために追加した一時ログ、観測結果、削除確認。
- 確定原因: 観測で確定した原因だけ。
- 採用する修正方針: 仕様が不足していない時のみ書く。構造が変わる場合は AS-IS（現状）と TO-BE（変更後）の 2 図で示す。図作法は `presentation` skill に従う。
- 禁止する修正: 新しい状態値の追加、症状だけを隠す分岐などを具体的に書く。

## 修正実行入力

- 承認済み修正方針: 恒久修正として採用する方針。
- 禁止する修正: 実装で許可しない対症療法。
- 影響ファイル候補: 観測事実に基づく候補。
- 再現手順と期待状態: 画面再現確認の再現手順と、修正後に満たすべき期待状態。
- 追加する fail-test の観点: 修正前に追加して fail を確認し、修正後に pass を確認する観点。
