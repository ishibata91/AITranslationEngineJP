# Investigation: mod-npc-name-derivation

`investigation.md` は不具合の再現と原因究明だけを持つ。どう直すかの設計は `design.md` が持つ。

## 観測済み問題

人間が mod を翻訳した実行で確認した 4 件。

- mod が追加した NPC について、本文中に人名が名のみ・苗字のみで出た時に固有名の機械置換が当たらない。フルネームでは当たる。
- `Sleeping Giant Inn` のような場所名が置換されない。公式の日本語訳が存在する語である。
- 台詞の訳文から句読点が消える。
- 訳文で話者の男女の区別がついていない。

## 画面再現確認

実 app の画面操作では再現していない。理由と代替手段を残す。

- 画面から抽出だけを実行する導線が無く、公開されている操作は抽出と翻訳を続けて行うものだけである（`internal/api/app.go` の `RunExtractAndTranslate` と `SubmitBatchTranslation`）。本 task の 4 件はいずれも AI 応答より前の段（抽出・供給・プロンプト組み立て）で決まるため、画面から再現するには mod 1 本ぶんの翻訳を実行する必要がある。
- 代わりに実データ結合テスト基盤（`cmd/goldcap`）で再現した。本番の C# 抽出器と実辞書を使い、AI 応答だけを決定的な代替実装へ差し替える基盤で、送信プロンプト全件と DB 最終状態を書き出す。原因の所在（供給とプロンプト組み立て）を直接観測できる。
- 実行した対象は `dictionaries/Data/inigo.esp`（公式訳を持たない mod）と `dictionaries/Data/HearthFires.esm`（公式訳を持つ Bethesda 製 DLC）の 2 本。

## 原因仮説

観測事実から立てた候補と検証順序。

1. 供給の穴: 固有名の確定訳語と参照訳の供給が、選んだ plugin が所有する record に閉じている。mod は日本語 Strings を持たないので供給が 0 件になる。場所名と名前派生の両方を説明できるため最初に検証する。
2. 派生経路の欠落: mod NPC のフルネームは実行内の AI 訳として確定するが、そこから部分形を派生する経路が無い。仮説 1 を直しても残るかを確かめる。
3. 指示文の既定値: 台詞の口調指示が句点を禁じている。送信プロンプトの文面で確かめる。
4. 性別の伝達: 性別が口調指示の文面に現れない。送信プロンプト全件の分布で確かめる。

## 確定原因

**1. 公式訳が供給されない（場所名の未置換と、破壊置換の原因）**

固有名の確定訳語と参照訳の供給は、選んだ plugin が所有する record についてのみ english と japanese の Strings を解決して作る。mod の record は公式日本語 Strings に存在しないので、日本語側が必ず空になり供給が 0 件になる（`internal/engine/engine.go` の `DeriveMasterTerms`、`internal/engine/reference.go` の `LoadReferenceTranslations`、C# 抽出器の 2 言語解決）。

画面警告の判定（`internal/api/strings_presence.go` の `GetStringsPresence`）は、選んだ plugin の親フォルダ配下の `strings/` を見て english と japanese のファイルが揃っているかで判定する。Data フォルダに公式の英日 Strings が置いてあれば警告は出ない。警告が立っている前提（Data フォルダ全体を供給源とみなす）と、供給の実装（選んだ plugin の所有分のみ）が食い違っている。

設計経緯として次を確認した。`docs/exec-plans/completed/strings-based-reference/design.md` の TO-BE 表は、変更前を「XML 群が base 全体を対象と無関係に供給。取込は plugin で絞らない」、変更後を「base ゲームかは判定せず、base ゲームを別途抽出対象にもしない」「対象 plugin 単位のまま」と記述している。人間の意図は「英日 Strings が揃うものは base かどうかを問わず全部供給する」であり、記述が「base を別途の抽出対象にしない」とも読める形になっていたため、供給が選んだ plugin 単位へ狭まる実装で通った。実データ確認は公式訳を持つ `Dawnguard.esm` だけで行われたため、mod を対象にすると 0 件になる帰結が観測されないまま完了した（`docs/changelog.md`）。

**2. mod NPC の部分形が派生されない**

派生（`DeriveMasterTerms`）は、抽出結果のうち日本語側が空でない行だけを入力にする。mod NPC は日本語側が空なので入力に入らない。加えて派生は抽出直後に実行され、固有名を AI で訳す段より前にある（`internal/api/app.go` の `prepareForTranslation` と `internal/engine/engine.go` の実行順）。mod NPC のフルネームは実行内の AI 訳として確定するが、その確定訳から部分形を派生する経路は存在しない。原因 1 を直しても、公式訳を持たない mod NPC については残る。

**3. 台詞の句読点が消える**

台詞の口調指示の既定値が句点を禁じている（`db/migrations/0006_record_type_translation.sql`）。

- 台詞は文末に句点を打たない。原文が疑問符・感嘆符で終わる時だけ ？ ！ を置く。
- 1 つの台詞に文が 2 つ以上ある時は、句点でつなげず全角空白で区切る。

あわせて役割語の例文 57 行からも末尾の句点を外してあるため、モデルは例示からも同じ形を学ぶ。commit `b4e06664`（2026-07-26）で公式既訳の集計（台詞の末尾句点 0%）を根拠に意図して入れた既定値であり、実装の誤りではない。人間の判定は「公式訳の実態以前に日本語として不自然」である。

**4. 性別が翻訳プロンプトへ伝わらない**

性別は口調指示の項目としては出力されず、役割語テンプレートを引くキー（性別 × 年齢区分 × 口調セル）としてのみ使われる（`internal/core/personatone/personatone.go` の `roleSpeechLines`）。プロンプトに載るのは引いた結果の一人称と言い回しだけである。

`assets/role-speech.tsv` の成人行は、男性が 4 つの口調セル（冷然・見下し / ぞんざい / 居丈高・罵倒 / 率直・興奮）でのみ一人称「俺」になり、それ以外は一人称「私」・言い回し空である。性別不明の行も一人称「私」・言い回し空であり、成人男性と性別不明の出力が完全に一致する。女性行だけが「女性らしい、やわらかな言い回しを基調にする。」という文を持つため、観測した偏り（女性 185 件・男性 0 件・一人称「私」8530 件）になる。
