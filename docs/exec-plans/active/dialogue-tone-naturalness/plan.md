# Task Plan: dialogue-tone-naturalness

会話の訳から機械翻訳感を消す実験 task。`/loop` で仮説と実測を繰り返す形で進めるため、設計を先に固めず、砂場・達成条件・接続先だけを固定する。

## 事象

人間が見たことだけを書く。

- 会話の訳が全体的に丁寧すぎて、機械で訳したような硬さが残る。
- 意訳が足りず、英語の構文をそのまま日本語へ写した訳になっている。
- クエストログと叙述系（物品説明、効果説明、書物、世界観断片）の訳は現状でも良い。

## 対象

会話だけを対象にする。`INFO:NAM1`（NPC の応答）で、対象 plugin は `inigo.esp`。

- 叙述系とクエストログは触らない。訳が既に良いので、変える理由が無い。
- `DIAL:FULL`（プレイヤーの選択肢文）も今回は外す。話者が NPC でなく、口調の指示が別の経路（汎用・PC 発話）で組まれるため、実験の変数が増える。
- 訳す件数は、話者・口調の区分・原文の長さで偏らないよう層別に選んだ数百件とする。ループを回すたび同じサンプルを訳し直すので、回の間で比較が成立する。

## 達成条件

**公式訳と判別できなくなること。** 公式日本語訳（`reference_translation` の `INFO:NAM1` 41,159 件）を人間の訳、自前の訳を機械の訳として判別する分類器を訓練し、判別できなくなることを条件にする。

分類器の作りを固定する。走らせた後に作りを変えない。

- 特徴は内容語を含まない文体だけにする。品詞の n-gram、助詞の分布、文末の活用形、文の数と長さ、句読点の分布。文全体を特徴にすると、分類器が話題や固有名（イニゴ、スキーヴァーなど）で判別してしまい、文体を測らなくなる。
- 分類器はロジスティック回帰にする。どの特徴が機械らしさに効いているかを係数と SHAP で出せる。
- 評価は層化 5 分割交差検証の AUC にする。両クラスの件数を揃えてサンプリングする。
- json の断片や対応しない括弧が混ざった行は訓練から外す。破損だけで判別できてしまい、文体を測らなくなる。

達成の線は、現状の判別精度（ベースライン）を測ってから 1 度だけ置き、以後動かさない。現状は 95% 前後で判別できる見込みで、それを偶然（AUC 0.5）へどこまで近づけるかを線にする。

**意味が保たれていること。** 判別器は機械らしさを測るが、意味の取り違えを測らない。`Thank you. That feels good.` を「結構です」と訳す誤りは、文体としては自然なので判別器を通る。参照なしの品質推定（COMETKiwi）で意味の保持を見張る。RTX4090 の Windows マシンで回す。

**訳文を後から加工して値を動かさないこと。** 値が動いたことは訳文そのものが変わったことを意味する状態を保つ。

## 診断に使う値（達成条件ではない）

判別器が機械と判定したときに、何が原因かを見るために測る。線は置かない。現在の値は `tmp/dialogue-tone-naturalness` を走らせて測った（訳が入った 183 件のうち破損 21 件を外し、162 件を数えた）。

| 数える値 | 現在 | 既訳 |
| --- | --- | --- |
| 敬体で終わる文を含む割合 | 63.6% | 5.9% |
| 一人称（私・俺・僕・わたし・あたし）を書く割合 | 42.6% | 9.6% |
| 二人称（あなた・君・お前・貴方）を書く割合 | 25.9% | 9.5% |
| 訳の文字数 ÷ 原文の文字数 | 0.680 | 0.439 |
| json の断片または対応しない括弧が混ざった行 | 21 件 | 0 件 |

敬体は訳文の文末の形で判定する（です・ます・ました・ません・でしょう・ください・ございます など）。「です・ます を含む」で数えると「ますます」「済ます」を誤って拾い、「ました」を拾い落とす。

文末の句点は測らない。自然さの原因ではなく、完全な文を作った結果の副産物であり、主語を落として常体にすれば結果として減る。

## 砂場

- 実験の道具と記録: `tmp/dialogue-tone-naturalness/`（`.gitignore` の 14 行目で除外されるので commit に入らない）。
- 触る正本: `assets/role-speech-examples.tsv`（口調の例文 57 行）、`assets/role-speech.tsv`（一人称と言い回しの傾向）、`internal/core/personatone`（種族に応じた注記）、`db/migrations/0006_record_type_translation.sql` の `口調` の seed 文面。

## 接続先

- 翻訳: `http://192.168.0.226:1234`（LM Studio、別マシン）。モデルは実験の条件として固定する。`hy-mt2-7b` は空応答と記号混入を起こすので使わない。gemma 系を使う。
- 判別器と品質推定: RTX4090 と 9800X3D の Windows マシン。判別器は形態素解析とロジスティック回帰なので CPU で足りる。参照なしの品質推定は GPU を使う。
- 数える対象の DB: `db/aitranslation.dev.sqlite3`。

## 出発点の観察

実験を始める前に確かめた事実を残す。仮説の出どころになる。

- **口調指示文は既に「台詞は文末に句点を打たない」を求めている。** それでも訳の 59.9% が句点で終わる。原因は口調の例文 57 行すべてが句点で終わっていることで、指示文と訳例が矛盾し、訳文は訳例に従っている。指示文へ言葉を足す形では効かない。
- **例文 57 行すべてが英語の主語をそのまま日本語へ写している。** `I work the forge here.` に対する成人女性の訳が「私はここで鍛冶の仕事をしています」で、既訳が一人称を書く割合 9.6% と離れている。
- **例文の敬体が女性の区分に偏っている。** 目で読んで数えると成人女性 5/9、年配女性 8/9 が敬体で、成人男性・年配男性・子供は 0/9。丁寧さが性別へ機械的に対応している。
- **種族に応じた注記が敬体を招く。** `internal/core/personatone` の `raceMarkerTrait` がカジートに三人称の自称を足し、例文由来の敬体と重なって「この者は、まだいくつか持っているような気がします」になる。
- **app が使う DB の口調指示文は画面編集済みで、migration のどの文面とも一致しない。** seed を直しても届かないので、指示文を変えるなら画面から入れる。
- **現在の 183 件は `hy-mt2-7b` の出力である。** 口調テンプレートを触る前に、現状のまま gemma で 1 度訳し直して基準を取る。テンプレートとモデルを同時に変えると、値が動いた原因を分けられない。破損 21 件はモデル側の問題で、gemma に変えるだけで消える見込みが高い。

## やらないこと

- 会話の場面を翻訳へ渡すこと（会話の種類、クエストの場面、応答が答えている選択肢文、同一応答の続き行）。後続 task で扱う。
- 会話の手前の連鎖を翻訳へ渡すこと（`LinkTo` の 1 段逆引き、作成順による並びの近似）。後続 task で扱う。
- 参照する既訳と 1 対 1 で突き合わせる指標（chrF++、参照あり COMET）。同じ原文の正解訳が要るが、`inigo.esp` の 183 件のうち正解訳を持つのは 8 件しかない。`Skyrim.esm` を訳す段になれば 41,159 件そろうので、そのときに判断する。
- 訳文の破損の原因を直すこと。判別器の訓練から外し、件数を診断として出すところまでとする。
- 叙述系とクエストログの訳の書き方を変えること。
