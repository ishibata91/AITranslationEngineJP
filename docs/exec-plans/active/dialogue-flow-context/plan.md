# Plan: dialogue-flow-context

`task_id`: `dialogue-flow-context`

`状態`: 未着手（`bulk-line-translation`（slice1）の master 取り込み後に着手する）

`依存`: `bulk-line-translation`（slice1: バルク翻訳機構。キー配列経路・部分成功・トークン予算チャンクの土台。この上へ会話文脈を乗せる）

## 私がやりたいこと

会話のやり取り（プレイヤー選択 → NPC 応答 → 次）の文脈を翻訳へ渡し、前後で噛み合った訳にする。狙いA（文脈で品質を上げる）の本体。

slice1 のバルクは「同一 INFO・同一話者・同一口調指示」の断片しか 1 リクエストにまとめず、会話をまたいだ文脈をモデルへ渡せていない（コスト削減の副次効果に留まる）。会話の往復・感情の移り変わり・クエストの流れをモデルに見せる仕組みを作る。

## 決まっていること

- 文脈の対象は「会話のやり取り」（方向1）にする。プレイヤーの選択肢と NPC 応答の往復の流れを、翻訳する台詞へ文脈として与える。
- 会話の流れ（どの発言がどの発言に続くか、選択肢と応答の対応）は現在の DB に無い。抽出（C#/Mutagen）で DIAL（トピック）・QUST（クエスト）・INFO の PNAM（前 INFO）連結を取り、スキーマへ保持するところから要る。known-issues no1 の「会話の流れ e7」と重なる（統合可否は本 task の設計で決める）。

## 検討が必要なこと（本 task の設計で詰める）

- リクエストの作り方: 会話 1 本を 1 リクエストにまとめて訳す（バルク。複数話者・複数感情が混ざるため行ごとに話者・感情のヒントを添える）か、訳す対象は 1 行にして周辺の会話を読み取り専用の文脈として添えるか。前者は狙いB（コスト削減）も効くが行ごとのヒント設計が要る。後者は品質分離が容易だがトークンが増える。
- 話者属性・感情の持たせ方: 複数話者・複数感情を 1 リクエストへ入れる場合に、行ごとの口調・感情指示をどう表現するか（キー単位のヒント、場面共通の system など）。
- 束ねる単位: 会話 1 本、同一 DIAL トピック、同一クエストのどれを 1 チャンクにするか。長い会話はトークン予算で分割し、root path 抜粋を文脈に添えるか。
- known-issues no1「会話の流れ e7」との統合可否。
- コスト（B）と品質（A）の釣り合い。文脈行を足すとトークンが増えるため、どこで釣り合わせるか。
