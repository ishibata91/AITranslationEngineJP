# 統合テストの指針

関連文書: [`coding-guidelines-tests.md`](./coding-guidelines-tests.md), [`architecture.md`](./architecture.md)

本書は、単体テストと UI 人間操作 E2E の間に置く統合テストの指針を定義する。
複数のクラス・エンティティをまたいで合成した結果が仕様通りかを、システムの入口から叩いて期待値と突き合わせて確かめる方法を対象にする。
テスト実装の一般規約は [`coding-guidelines-tests.md`](./coding-guidelines-tests.md) を正本にし、本書はその統合テスト部分を詳述する。

## 1. 位置づけ

**単体テストが届かない範囲を、実画面確認より軽く守る。**

- 問題: 単体テストは 1 つのクラス・エンティティの中しか守らない。複数をまたいで合成した結果が仕様通りかは、単体では観測できない。
- 対象: C# 抽出機と Go メインシステム（翻訳）の各々で、合成した結果の仕様適合。
- 他テストとの分担:

| テスト種別 | 守る対象 | 観測点 |
| --- | --- | --- |
| 単体 | 1 単位の分岐・エラー経路・純粋ルール | 各 package・クラスの単体テスト |
| 統合（本書） | 複数のクラス・エンティティをまたいだ合成の仕様適合 | C# = `tools/extractor.Tests`、Go = `internal/harness` |
| UI 人間操作 E2E | 人間操作の主要 flow、表示、AI 訳の妥当性 | 実画面確認。重いので統合テストでは扱わない |

## 2. 形

**合成入力を作り、実際の入口を叩き、期待する結果と突き合わせる。**

- システム単位: テストはシステムごとに書く。C# は抽出機、Go はメインシステム（翻訳）。両者を横断する共有の仕組み（分類体系・被覆機構・汎用 runner）は作らない。
- 入口: 各システムが本番で通る入口をそのまま叩く。C# は合成 plugin を抽出し、Go は合成入力を翻訳へ通す。
- 突き合わせ: その合成でしか観測できない結果を、期待値と比べる。1 シナリオ 1 期待にし、テスト名がその仕様を語るようにする。

## 3. 期待値の高度v

**その合成でしか観測できない具体的な結果を期待にする。全ダンプの golden 凍結でも、抽象的な分類体系でもない。**

- 期待値はテストに読みやすく直書きする（別ファイルの仕様真や、仕様の分類体系を作らない）。
- 入れる例: 本文中の固有名が確定訳へ置換されて送られる、台詞が話者へ連関して抽出される、翻訳対象外が訳されない。
- 入れない: 中心 DB の全行・全列の凍結ダンプ（実装表現が変わるたびに壊れ、仕様の変化と区別できない）。単段で純粋に検証できるルール（単体テストに残し、重複させない）。

## 4. テストダブルと決定性

**継ぎ目はテストダブルで跨ぎ、非決定を排す。**

- 継ぎ目: 1 プロセスで C# と Go を結合しない。Go 側は抽出後の状態を seed するダブルで継ぎ目を跨ぐ。C# 側は master 無しの自己完結 plugin を構築して抽出する。
- 翻訳 provider: 決定的 fake で固定する。AI 訳の非決定を排し、AI 訳の妥当性は実画面確認へ委ねる。
- 決定性: 実 .esm・実 LLM・dotnet 実行時の実データを使わない。出力を入力とコードだけに依存させる。

## 5. 置き場所と完了条件

- 置き場所: Go は `internal/harness`、C# は `tools/extractor.Tests`。各システムのテストの近くに置く。
- 完了条件: Go は `go test`（`npm run verify:backend` が束ねる）、C# は `dotnet test tools/extractor.Tests` が通る。
- coverage 目標は個別 task の承認済み条件がある場合だけ完了条件にする。
