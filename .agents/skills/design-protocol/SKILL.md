# Design Protocol

## 入力

- 要求: 設計が満たす内容と要求を識別できる番号。
- 対象: 設計対象の repository または source。
- 参照: `references.md` がある場合は source の path、symbol、外部資料の所在を参照 ID として受け取る。
- 確定済みの事実と制約: 原因、外部仕様、変更できない条件がある場合だけ受け取る。
- 出力先: 指定がある場合だけ受け取る。

入力の名前、保存場所、作成元の工程を前提にしない。

## 設計を作る

要求ごとに次の順で書く。

### 現況の理解

- 変更対象の責務を書く。
- doc comment、schema、migration、型、test が明記する不変条件を書く。
- 根拠となる source は参照 ID で示す。
- 要求が扱う対象の単位と、既存の受け皿が持つ key の単位を並べる。
- 判断に使わない呼び出し関係の写しは残さない。

既存実装は現況として扱い、変更後も守る制約とはみなさない。

### あるべき形

- 要求を満たした状態の責務配置を書く。
- 現況との差分ではなく、変更後の構造として書く。
- state、処理、永続化、外部接続の所有者を書く。
- 適用範囲と永続性を書く。
- 確定済みの事実と制約がある場合は、成立させる構造を示す。

流れ、関係、責務が変わる場合は、現況とあるべき形を別々の図で示す。
図を添える場合も、設計の説明は文章だけで成立させる。

## 未決定事項

設計を確定するために人間の判断が必要な論点は `pending.md` へ返す。

次の状態は未解決の論点として扱う。

- 要求が扱う単位と受け皿の key の単位が異なり、寄せる先を決められない。
- 複数の責務配置が要求を満たし、採用基準がない。
- 確定済みの事実または制約と要求が両立しない。
- 根拠 source を参照 ID へ対応付けられない。

## 書かないこと

- 利用者から観測できる振る舞いの仕様。
- test case と test 実装。
- 原因の調査過程。
- 承認順序、実行順序、呼び出し元、次の工程。
- 作業管理用の識別子と保存場所。
- 設計を検証したという自己判定。
- source の path、symbol、外部資料の所在。

## 返す成果物

- 要求ごとの現況の理解とあるべき形。
- 根拠にした参照 ID。
- `pending.md` へ追加する未決定事項。
- 指定された出力先へ書いた場合は出力先の path。

## 完了条件

- 全ての要求に現況の理解とあるべき形がある。
- 現況の理解に参照 ID の根拠がある。
- 未解決の判断が `pending.md` へ分離されている。

## 停止条件

- 要求または対象 source が不足する。
- 要求と確定済みの制約が両立しない。
- 人間の判断なしに責務配置を一つへ絞れない。

停止時は、不足項目、衝突箇所、判断できない論点を返す。
