# Design Protocol

## 目的

`design-protocol` は、`design.md` と `spec.md` の書き方と、両者に対する `design-review` の検証内容を固定する作業プロトコルである。
新規実装フロー（`feature-workflow`）と修正フロー（`fix-workflow`）が同じ規約を読む。各入口 skill は、いつ書くか（依存順、承認順）を持つ。

`design.md` は人間が読んで判断する説明を持つ。`spec.md` は下流の段が実装根拠にする仕様を持つ。両者が食い違う場合は `spec.md` を優先する。
両 file は `plan.md` の要求ごとの節に分ける。

## 対応役割

- Codex 本体が task 文脈を持ったまま読んで適用する。
- `design-review` は `design_reviewer` agent（`fresh`、読み取り専用）が担う。
- 呼び出し元は `feature-workflow`、`fix-workflow`、または同等の入力を渡す上位 skill とする。

## 呼び出し元から渡される情報

- task-id: 作業計画フォルダを特定する識別子。
- 作業計画フォルダ: `design.md` と `spec.md` を置く `docs/exec-plans/active/<task-id>/`。
- フロー種別: 新規実装フローと修正フローのどちらか。
- 根拠: `plan.md` の要求欄。修正フローは `investigation.md` の確定原因も受ける。

## 作業前に読む正本

- `design.md` の雛形: `docs/exec-plans/templates/task-folder/design.md`。
- `spec.md` の雛形: `docs/exec-plans/templates/task-folder/spec.md`。
- 図作法: `presentation` skill。
- 語の正本: `docs/vocabulary.md`。
- 外部成果物が不足または衝突する場合は停止し、衝突箇所を返す。

## 要求ごとの節

Codex 本体は、`design.md` と `spec.md` を `plan.md` の要求ごとの節に分ける。節の見出しに要求番号と要求の見出し文を書き、節と節の間に区切り線を置く。

どの要求の節にも置けない内容を書かない。置き場所が無い内容は、要求欄へ足すことを人間へ諮るか、捨てる。

## design.md

Codex 本体は、各要求の節へ次の 3 つを書く。

- 現況の理解: 触る器（table、package、file）が持つ役割と、その器が doc コメントや migration で明記している不変条件を書く。要求が扱う対象の単位と、受け皿が持つキーを並べて書く。単位が違う場合は、どちらへ寄せるかを `検討が必要なこと` へ回す。
- あるべき形: 要求を満たす形を書く。現況との差分としては書かない。何がどの器を持ち、適用範囲と永続性は何かを示す。
- 変更点: あるべき形を成立させるために触る file と関数を挙げ、そこをどう変えれば成立するかを書く。場所を挙げられない変更点は書かない。

`design.md` の末尾へ `検討が必要なこと` を置く。人間の回答なしに先へ進めない論点を書き、論点がなければ「なし」と書く。

Codex 本体は、既存実装を現況として扱い、制約として扱わない。責務の分け方が変わる場合は、既存の呼び出し関係を作り直す案を書く。既存の呼び出し関係の写しは `design.md` へ残さず、判断に効いた事実だけを残す。

フロー種別で次を足す。

| フロー種別 | 各要求の節に足すこと |
| --- | --- |
| 新規実装フロー | 現況の理解に、要求が扱う対象を今どの器が持っているかを書く |
| 修正フロー | `investigation.md` の確定原因に対応する直し方を書く。症状だけを隠す対症療法（新しい状態値の追加、症状を隠す分岐）を避ける |

流れ・関係・責務が変わる箇所は、現況とあるべき形の 2 図を文章に添える。図作法は `presentation` skill に従う。図を添える場合も、説明は文章で成立させる。

## spec.md

Codex 本体は、各要求の節へ仕様を入れ子の箇条書きで書く。設計理由、変更手順、図は `design.md` が持つ。

第 1 段に仕様を書き、要求番号から続く番号を振る。第 2 段に次の 3 つを書く。

- 前提条件: その仕様が問われる状況を書く。状況を選ばずに成立させる場合は「なし」と書く。「なし」と書いた仕様が、状況によらず成立させる振る舞いになる。
- 確かめ方: 何を見れば成立が分かるかを、人間が触れる物（画面、出力ファイル、送信する指示の文面、訳された本文）で書く。
- 対応する実テスト: 本 skill では空にする。`implementation-module` が最終検証で埋める。

確かめ方が空欄になる仕様は、要求から見えない仕様なので捨てる。

Codex 本体は、各要求の節へ次の 3 つを揃える。

- 正常系: 要求が想定する状況で、要求どおりに動く仕様。
- 対象に入る側の境界: 要求が扱う対象の端にあり、それでも要求どおりに動く状況の仕様。
- 対象に入らない側の境界: 要求が扱う対象の外にあり、要求どおりの動きをしない状況の仕様。

3 つのどれかを書けない要求は、書けない理由を `design.md` の `検討が必要なこと` へ書く。

記述を次に拘束する。

- 仕様の主語と目的語は、要求の文に現れる語か、`docs/vocabulary.md` にある語で書く。
- 新しい名詞が要る場合は、`docs/vocabulary.md` へ足すことを人間へ諮る。足さない場合は名詞を作らず、動作を説明する文で書く。
- 仕様の語尾は「〜こと」で終える。この文をそのまま実テストの test case 名として使う。
- 要求のうち今回満たさない部分がある場合は、その要求の節へ 1 文で書く。無ければ書かない。

フロー種別で次を足す。

| フロー種別 | 各要求の節に足すこと |
| --- | --- |
| 新規実装フロー | 仕様は変更後に成立させる振る舞いとする |
| 修正フロー | 仕様は、実装への引き継ぎで渡す fail-test の観点と同じ文にする |

## design-review

`design-review` は、人間レビューの前に、実現可能でない案と誤読の余地がある記述を否決して人間との往復を減らす AI 検証である。両フローで通す。

- 入力: `design.md` のパス、`spec.md` のパス、`task-id`、対象 repo のルート、フロー種別。
- 検証内容:
    - 現況検証: `design.md` の現況の理解を根拠ソースの場所と照合し、器の役割と不変条件が実ソースで成立しているかを確かめる。
    - 変更点検証: `design.md` の変更点を実ソースへ踏み込んで確かめ、成立しない主張を否決する。
    - 漏れ検出: 変更予定箇所の列挙から漏れた影響先（呼び出し元、依存先、同じ前提を持つ別箇所）を確かめる。
    - 記述検証: `spec.md` の各仕様に、要求番号と前提条件と確かめ方が書かれているかを項目ごとに見る。空欄がある行を挙げて否決する。仕様の語尾が「〜こと」で終わっているか、主語と目的語が要求の文または `docs/vocabulary.md` にある語で書かれているかを見る。`docs/vocabulary.md` に無い名詞を使う行を挙げて否決する。
    - 出どころ検証: `spec.md` の各仕様が `plan.md` のどの要求の節にあるかを見る。要求の節に置けない仕様を挙げて否決する。
    - 網羅検証: `spec.md` の各要求の節に、正常系、対象に入る側の境界、対象に入らない側の境界が揃っているかを見る。欠けている要求番号を挙げて否決する。
    - 整合検証: `design.md` のあるべき形と `spec.md` の仕様が同じ振る舞いを指しているかを確かめる。`design.md` にあって仕様に無い振る舞いは漏れ候補として返す。
- 修正フローで足す検証: `design.md` の修正方針が `investigation.md` の確定原因に対応しているかを確かめる。確定原因から離れた直し方は否決する。
- 判断範囲: 成立可否の判定、記述違反の指摘、漏れの指摘だけを行う。設計の好み、代替案の選定、実装、`design.md` と `spec.md` の書き換えは呼び出し元が扱う。
- 出力: 判定（通過または否決）、否決理由（照合したソースの場所または該当行つき）、漏れ候補の一覧。戻し先は呼び出し元。
- 否決時: Codex 本体が同じ文脈で `design.md` または `spec.md` を書き直し、`design-review` を再実行する。否決理由を解消できない場合は人間へ論点として上げる。

## skill が扱わない対象

- いつ書くか（依存順、承認順、下流への引き継ぎ）は各入口 skill が扱う。
- 実装範囲の scope 列挙とテスト設計は `implementation-module` が扱う。
- 再現確認と原因究明は `fix-decision` と `investigation.md` が扱う。
- 人間レビューの依頼と承認判定は各入口 skill が扱う。
- docs 正本反映は `finalization-module` が扱う。

## 返す成果物

- design.md パス: 作成または更新した `design.md` の場所。
- spec.md パス: 作成または更新した `spec.md` の場所。
- 確定仕様の要約: `spec.md` の要求ごとの仕様。
- design-review 判定: 通過または否決、否決理由、漏れ候補。
- 未解決の論点: `検討が必要なこと` に残る、人間回答が要る論点。

## 作業を完了できる条件

- `design.md` の各要求の節に現況の理解、あるべき形、変更点が書かれ、末尾に検討が必要なことが書かれている。
- `spec.md` の各要求の節に、正常系と 2 つの境界の仕様が書かれ、各仕様に前提条件と確かめ方が書かれている。
- `design-review` の判定が、全ての現況の理解、全ての変更点、全ての仕様行に付いている。
- `design-review` が通過している。

## 作業を止める条件

- 作業計画フォルダ、フロー種別、根拠のいずれかが不足する。
- 仕様が `plan.md` のどの要求の節にも置けない。
- `design.md` の変更点に file と関数を書けない。
- `design-review` の否決理由を書き直しで解消できない。
- 停止時は不足項目、衝突箇所、固定できない判断、戻し先を返す。
