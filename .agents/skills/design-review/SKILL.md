# Design Review

## 目的

`design-review` は、人間が承認する前に、設計と仕様が要求された利用者の目的を、既存実装の制約内で実現できる状態かを確かめる検証技能である。

設計の好み、一般的な注意点、代替案の提案は扱わない。

## 入力

- 要求。
- 設計。
- 仕様。
- 未決定事項。
- 参照。
- 対象 repository または source。
- 語彙の正本がある場合は正本。
- 確定済みの事実と制約がある場合は該当資料。

入力の名前、保存場所、作成元の工程を前提にしない。

## 実行境界

- 読み取り専用で検証する。
- 設計と仕様を書き換えない。
- 代替案を選ばない。
- 実装しない。
- 人間の設計判断を代行しない。

## 最初に確かめること

reviewer は、要求から解決したい利用者の目的を1文で書く。

`pending.md` が空でない場合は停止する。設計と仕様の細部はレビューしない。

要求が現在の問題、解消した状態、制約のいずれかを欠き、目的を固定できない場合は `目的未固定` を返す。設計と仕様の細部はレビューしない。

## 確認する範囲

reviewer は、次の関係だけを確認する。

- 要求された目的を、設計の責務と変更が実現するか。
- 設計の責務と変更を、仕様が実装可能かつ検証可能な振る舞いへ落とせているか。
- 現在の source、呼び出し元、依存先、不変条件が、設計の実現を妨げないか。

指摘は、目的を実現できるか、または設計と仕様を実装・検証できるかの結論を変える場合に限る。

reviewer は、軽微な記述の改善、網羅的なリスク一覧、将来の拡張、好みによる代替案を返さない。

## 設計を検証する

- 現況の理解を参照 ID が指す source と照合する。
- 責務と不変条件が実ソースで成立しているかを確かめる。
- あるべき形が要求を満たす責務配置になっているかを確かめる。
- 参照 ID が指す source を開き、あるべき形が実現可能かを確かめる。
- 呼び出し元、依存先、同じ前提を持つ実装の漏れを探す。
- 確定済みの事実と制約がある場合は、設計が内容に対応しているかを確かめる。
- 根拠を確認できない主張は通過させない。

## 仕様を検証する

仕様ごとに次を確かめる。

- 対応する要求番号がある。
- 仕様文が「〜こと」で終わる。
- 前提条件と確かめ方が埋まっている。
- 主語と目的語が要求または渡された語彙にある。
- 正常系、対象に入る側の境界、対象に入らない側の境界が要求ごとに揃っている。
- 要求にない振る舞いを追加していない。

違反する仕様は該当箇所を挙げて否決する。

## 設計と仕様を照合する

- 設計のあるべき形と仕様が同じ振る舞いを指しているかを確かめる。
- 設計にあって仕様にない振る舞いを漏れ候補として返す。
- 仕様にあって設計で成立させられない振る舞いを否決する。
- 要求にあって設計と仕様の双方にない内容を漏れ候補として返す。

## 判定

全ての検証項目に根拠を付けられる場合だけ通過とする。
一つでも成立しない項目または確認できない項目がある場合は否決とする。

設計の好みは判定理由にしない。

判定は `通過`、`目的未固定`、`否決` のいずれかとする。

## 再レビュー

呼び出し元は、最初の検証を含めて最大3回まで、同じ `design_reviewer` を再開する。

各回は、前回の判定、直した設計または仕様、現在の成果物を reviewer へ渡す。

3回目は新しい論点を追加しない。3回目で `目的未固定` または `否決` が残る場合は、残る理由と目的を実現できると判断できない理由を返して終了する。

## 返す成果物

- 判定: `通過`、`目的未固定`、`否決` のいずれか。
- 解決したい目的: 要求から読み取った1文。
- 否決理由: 対応する要求、文書の該当箇所、照合した参照 ID。
- 漏れ候補: 目的の実現または実装・検証を妨げる、呼び出し元、依存先、要求、設計、仕様の不足候補。
- 確認できない項目と不足資料。

## 完了条件

- 設計の全ての現況とあるべき形に判定がある。
- 全ての仕様に判定がある。
- 要求、設計、仕様の対応に判定がある。
- 判定理由に文書または参照 ID がある。

## 停止条件

- 要求、設計、仕様、対象 source のいずれかが不足する。
- `pending.md` が空でない。
- 入力同士が衝突し、正とする入力が決まっていない。
- 実行環境で根拠 source を読めない。

停止時は、不足項目、衝突箇所、検証できない範囲を返す。
